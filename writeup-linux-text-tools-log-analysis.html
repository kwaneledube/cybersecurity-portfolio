Linux text tools and log analysis

grep · find · pipes · redirection · brute-force pattern

Goal

Learn the command-line tools analysts use to read logs (head, tail, grep, find, pipes and redirection), and use them to work out what happened in a small login log.

Tools and environment

Kali Linux on WSL2, isolated from my Windows drive. The log is a 15-line file I invented myself. Its IP addresses come from ranges reserved for documentation, so they point at no real systems. I also kept practising on a beginner command-line wargame, and I follow its rules by not publishing solutions.

Steps

  1. Created the log in a practice folder with a here-document (cat > access.log << 'EOF'). Each line has a date, a time, an event (login, file read, permission denied), a status and the user or IP.
  2. Counted the lines with wc -l (15) and the failed logins with grep -c (8).
  3. Filtered the failures for one user by piping one grep into another.
  4. Counted failures per IP address with a pipeline, built one stage at a time so I could check each stage:
grep FAILED access.log | cut -d' ' -f6 | sort | uniq -c | sort -rn

The result was 6 failures for one IP and 2 for another.

  1. Read the story in the log. The IP with 6 failures tried three different account names (admin, root and test), and then logged in successfully as admin at 14:13:31.
  2. Saved the failed lines into their own file with >, and added a note with >>.

What the log showed

Many failures against common account names from one IP, followed by a success from the same IP, looks like a password-guessing attack that worked. I would treat the admin account as compromised: check what it did after 14:13:31, reset the password, block the IP, and add a failed-attempt limit and multi-factor login.

What went wrong

  • I overwrote my own log. I ran ls -l > access.log by mistake, and > replaces everything in a file. The log was gone. Fix: I rebuilt it from the commands I had used to create it. Habit now: make a backup with cp before experimenting, and double-check what follows every >.
  • An empty delimiter. I typed cut -d'' and got "the delimiter must be a single character". I fixed it by putting a space between the quotes: -d' '.
  • A search that returned 0 because of one character. I searched for PERMISSION DENIED with a space, but the log says PERMISSION_DENIED with an underscore. grep matches exact text. Habit: when I expect a result and get 0, compare my search text with the real file before trusting the 0.
  • A typo in an appended line made my file 10 lines instead of 9. I rebuilt it from the source log instead of editing by hand.
  • I misread the evidence. My first analysis blamed the wrong IP. Re-reading the output line by line, and naming the IP, the usernames and the time order, fixed it.
  • On the wargame I forgot the port. Connecting without -p tried the default port and failed with "Permission denied (publickey)". I also typed the port number on its own line, which the shell tried to run as a command. The port belongs after -p in the same command.
  • Mismatched quotes (opening with " and closing with ') left the shell waiting for more input with a > prompt. I stopped it with Ctrl+C.
  • I used cat on binary files and the terminal filled with garbage characters. The file command tells me what kind of file something is before I print it.

What I learned

  • tail shows the newest log lines, and tail -f follows a log as it grows.
  • grep filters lines. -c counts them, -i ignores case, -n shows line numbers and -v shows lines that do not match.
  • A pipe sends the output of one command into the next. sort | uniq -c counts repeated lines, and sort must come first because uniq only groups lines that sit next to each other.
  • > overwrites a file and >> appends to it.
  • find locates files by name, type, size or permissions. For example, it can look for world-writable files.
  • Check the file type before printing an unknown file.

Defender's view

  • Logs are evidence, so protect them. My accidental overwrite shows how easily a log can be lost. Real systems limit who can write to logs, keep backups, and send copies to a separate log server so a single mistake or an attacker cannot erase the only copy.
  • Work on copies. An analyst keeps the original log untouched and does the filtering on a copy.
  • Detecting brute force. The pattern "many failed logins, then a success from the same IP" is a classic alert. It can be caught with failed-attempt counts per IP and per account, lockouts, rate limits and multi-factor login.
  • Be careful with unknown files. Check the type before you print them, because binary data can garble a terminal and can hide things.
